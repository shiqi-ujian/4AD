# 4AD 问题处理维护手册（Agent SOP）

> 本手册是 agent 每次被定时唤醒后对 4AD 项目（`E:\yingren\4AD`）的处理规程。唤醒源：主会话 dsh-schedule 每 60 分钟统一巡检（4AD / 5z / chm-web 三项目一轮完成）。
> 相关路径均相对仓库根 `E:\yingren\4AD`。

## 0. 职责

群友通过腾讯文档收集表（链接发 QQ 群）提交问题 → 系统定时读取到 `问题收集/inbox/` → 本 agent 自动 debug、修复、发布到 GitHub Pages（`https://shiqi-ujian.github.io/4AD/`），并把结果写入网站「更新日志」页公示。

**安全铁律（违反即事故）**：
- `问题收集/`、`tools/feedback-bridge/config.json`、共享登录 profile、`feedback-state.json` 都已在 .gitignore 中，**严禁** `git add` 或提交其中任何内容（公开仓库）。
- 推送前必须 `git status --short` 检查变更清单，确认无敏感文件。
- **绝不手改发布产物**：`2_工具/hexmap.dist.html` / `combatmap.dist.html` 由 `build.js` 打包生成，修复必须落在源码（`2_工具/hexmap/`、`2_工具/combatmap/`），发布时跑 `node build.js` 重新生成。

## 1. 每轮处理流程

1. **读告警**：检查 `问题收集/alerts.md`（读取桥写入的告警）。有内容 → 先处理（如提示用户重新登录），处理完清空该文件。
2. **读取收集表**：运行 `node tools/feedback-bridge/collect-docs.mjs`（或确认读取桥/手动导入已把新问题放进 `问题收集/inbox/`）。
3. **列出 inbox**：`问题收集/inbox/*.json` 全部为待处理。无新问题 → 一句话结束本轮，不输出长文。
4. **逐条处理**（见第 2、3 节）：
   - 能定位并安全修复 → 修复 + 校验 → 计入本批发布。
   - 无法复现 / 描述不清 → `status: "need-info"`，在 `resolution` 写明缺什么信息，记入 changelog 的 pending 列表公示。
   - 需要用户决策 → `status: "blocked"`，在会话里说明并留待用户处理。
5. **发布**（本批有修复时）：见第 4 节。
6. **更新日志**：见第 5 节。
7. **收尾**：处理完的 inbox 文件移入 `问题收集/done/`（保留原 JSON，`status` 更新为 done，`resolution`/`released`/`doneAt` 填好）。

## 2. 修复来源定位表

| 问题类型 | 修复位置（源） | 说明 |
|---|---|---|
| 翻译内容错误（错别字/漏译/术语不一致） | `1_翻译/*.md`、`3_术语与数据/` | 术语先查 `3_术语与数据/_术语对照表` |
| hexmap 工具 bug（六角格地图） | `2_工具/hexmap/` 源码：`index.html` + `js/*.js`（config/state/core/render/interact/ui/generate/stats/init/ai） | **绝不手改 `hexmap.dist.html`**；发布时 `node 2_工具/hexmap/build.js` |
| combatmap 工具 bug（战斗地图） | `2_工具/combatmap/` 源码 | 版本号**小步递增**（v0.81→v0.82…，禁止跳 0.9/1.0）：同步改 `config.js` 的 `COMBATMAP_VERSION`、`index.html` 标题/页脚，并在其 `CHANGELOG.md` 顶部加小节 |
| squaremap / citymap | （已冻结，不主动改） | 需要的能力迁移到 hexmap/combatmap |
| 网站首页/入口 | `web/index.html`、`web/更新日志.html` | Pages 发布源 = `web/`（CI 里 `cp -r web/* _site/`） |
| 构建/发布工具 | `2_工具/*/build.js`、`.github/workflows/deploy-pages.yml` | 改动后务必本地跑 build 演练再发布 |

定位辅助：先在线上站点（https://shiqi-ujian.github.io/4AD/）或本地复现/核对问题，再反查对应源码。hexmap 大括号不匹配（白屏）→ 运行 `node 2_工具/brace_check.js`。

## 3. 校验

- JS 语法：`node --check <文件>`；hexmap/combatmap 打包自带 `new Function` 语法校验（`node build.js` 报错即失败）
- hexmap 大括号平衡：`node 2_工具/brace_check.js`（白屏排查）
- 页面交互验证：参照 5z 模式写临时无头 Edge CDP 验证脚本（`_test-*.mjs`，gitignore 已忽略），或本地起静态服务人工核对
- 翻译内容：对照 `3_术语与数据/_original_en.json` 核对原文

## 4. 发布

```bash
git add -A
git commit -m "fix: 修复 <问题id> <标题>（若为多问题批量：fix: 修复反馈问题 <ids>）"
git push
```

- 发布 = push main → GitHub Actions（deploy-pages.yml）自动构建 hexmap/combatmap dist 并部署 Pages。
- hexmap/combatmap 修复：**先本地跑 `node 2_工具/hexmap/build.js`（或 combatmap）**，确认 dist 生成成功、语法校验通过，再一并提交（源码 + 重新生成的 dist + CHANGELOG）。
- 发布前先 `git status --short` 检查变更清单（确认无 `问题收集/`、config.json 等敏感文件）。
- 推送失败：remote 是 **SSH**（`git@github.com:shiqi-ujian/4AD.git`）。先重试一次；再失败检查 ssh-agent / `C:\Program Files\Git\mingw64\bin\git-credential-manager.exe` 凭据；仍失败则保留本地提交，在会话中提示用户，下次巡检先 `git status` 补推。
- 可选：若 main 直推不稳，可用 GitHub PAT（GCM 读取）创建/合并 PR 代替（见 CLAUDE.md）。

## 5. 更新日志维护

1. 编辑 `tools/changelog.json`：在本批对应 entry 的 `fixes` 追加 `{id, title, detail, page}`；无法处理的追加到 `pending` `{id, title, note}`；如跨天可新建 entry。
2. 运行 `node tools/gen-changelog.mjs` 重新生成 `web/更新日志.html`，随本批发布提交。
3. 工具修复额外按工具自身约定追加：`2_工具/hexmap/CHANGELOG.md`、`2_工具/combatmap/CHANGELOG.md`（combatmap 还需按版本约定同步版本号）。

## 6. 特殊情形

- **读取桥告警（alerts.md 有内容）**：通常是未登录或页面结构变化 → 提示用户运行 `tools/feedback-bridge/login-docs.bat` 重新登录（共享 profile，一次登录覆盖 4AD + chm-web），或 `collect-docs.mjs --probe` 后根据输出校准提取逻辑；期间可继续处理已入库问题。
- **表单截图附件**：读取桥尽力下载到 `问题收集/attachments/<id>/`，缺失时按描述判断即可。
- **重复问题**：读取桥按内容哈希去重；处理时若发现与 done 中问题重复，合并并注明。

## 7. 运行前提（提醒用户）

- Harness 服务运行中，且主会话保持打开（schedule 到期才能准时唤醒；关闭期间到期项会在重开后补处理）。
- 读取桥共享登录态有效（定期用 `login-docs.bat` 刷新）。
- Node.js、git 凭据可用（SSH key 或 PAT）。
